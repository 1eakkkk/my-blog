## 重试、异常与安全恢复

| 情况 | 处理方式 | 必须保留的判断 |
| --- | --- | --- |
| 发布超时 / 响应丢失 | 重读同一 D；若已有 `previousContent`，连同原 manifest / snapshot 复用；无既有结果时才复用本次已固定的正文 | 不重新生成正文；回执未核实前不称成功 |
| 人工修改展示正文 | 重试使用服务端 `previousContent`，核对同一回执 | 不用展示正文覆盖原请求；不覆盖人工修改 |
| `SOURCE_FAILED` / `SOURCE_INTEGRITY_FAILED` | 报错；仅暂时错误按提示词有限重试 | 不转为 `SKIPPED_EMPTY`，不发布伪完整日记 |
| `CONFLICT` | 停止并对照永久登记与已接收正文 | 不覆盖、不换日期绕过、不清 registry |
| `POST_DELETED` 或 `deleted=true` | 停止；记录原 postId 与永久日期占用 | 物理删除不释放日期，不能重建同日测试帖子 |
| 授权过期 / 撤销 / 权限不足 | 记录实际挑战或错误；需要重新授权时交给负责人走官方交互 | 人工介入须记录，该次不算无人值守刷新通过 |
| `TOOL_CALL_BLOCKED_BY_SAFETY_CHECKS` | 保存用户提供的结果并与已有读取编号关联；按既定规则暂停本机验收观察，保留真实任务和授权 | 不臆测详细理由，不补跑或规避平台检查，不把既有回执当作本次新发布成功 |
| 回执不完整、manifest 变化或状态不明 | 标记 `RECEIPT_UNVERIFIED` / 对应失败并停止 | 不凭输出文字、HTTP 200 或数据库行数猜成功 |

受控异常测试可由负责人在授权范围内撤销**独立 P0** grant，再观察同一真实任务的失败与通知；不要撤销其他应用或直接清空 KV。`revoke` / `revoke-all` 通过一次性 operator 票据与官方 provider 撤销路径工作，只输出撤销数量。撤销结果、后续拒绝以及真实通知送达是三份不同证据；CLI 成功不能代替后二者。不要在两个待验午夜之间注入故障而仍把被干扰的序列算成连续成功；异常观察单独记录，必要时重新安排完整的连续两晚观察。

空日 / late 规则需保留但不编造：未来成功空源才可登记 `SKIPPED_EMPTY`，七天内可明确标记迟到补发；`sourceFailed` 永远不视为空。当前 P0 固定非空 synthetic fixture 没有真实聊天覆盖能力，也不能凭它宣称 P1–P4 或完整归档已完成。

## 恢复既有任务的流程

以下是恢复说明，不代表已执行，也不授权改变全局设置。

1. 先在仓库外保存实验结束时的原 task ID、提示词版本、可见计划、启用状态、插件连接与脱敏证据。保留永久日期登记，不通过删库隐藏失败或重置日期。
2. 在**同一 ID** 的任务编辑界面，从受保护的 `outputs/ai-diary-p0/task-original.json` 恢复原 `prompt`。只在任务界面使用原文，不将它写入仓库、报告或公开日志；不删除 / 重建任务，也不创建重复计划。
3. 对照备份核对标题、每天 00:00、目标 `Asia/Singapore` 和启用状态。原备份时区并未独立核实，如当前界面仍无字段，明确记录这一限制，不能声称恢复了已验证的时区配置。
4. 保持全局推送 / 邮件设置。备份的 `notificationsReported=disabled` 未独立核实，不能据此改变通知。任何超出原任务的通知调整须另行由用户决定。
5. 如负责人结束独立实验，按授权范围撤销 P0 grants 并核实后续调用拒绝；不直接删除 OAuth KV 数据，不影响其他插件。是否解除或卸载 P0 插件单独由负责人按用户授权处理。
6. 保留受保护的证据、原始备份与永久 registry。仅需清理 synthetic 展示帖子时，使用固定测试表的清理操作；物理删除后日期仍占用。资源下线、生产接入和真实聊天采集不属于本说明的自动操作。

即使恢复完成，未发生或未取证的连续两午夜、离线、自动刷新与通知仍保持 `UNVERIFIED`。验收失败和平台限制必须随结果说明保留。
